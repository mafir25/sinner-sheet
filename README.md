# Mephistopheles Terminal (Project Moon 5e)

Статический сайт + Ширма (React, `shirm-app/`) + Редактор карт (React, `map-app/`). Сборка: `npm ci && npm run build` → `dist/` (Vercel делает это сам).

## Структура

| Путь | Что это |
|---|---|
| `index.html` | главная (хаб) |
| `navigation.html` | База знаний: архетипы, классы, черты, снаряжение, правила, бестиарий, Э.Г.О. гифты, статусы, лор. Логика — `site/navigation.js`. Поиск по всей базе — **Ctrl+K** или **/**; у каждой карточки кнопка «Ссылка» (`navigation.html#раздел/Имя`) |
| `builder.html`, `egobuilder.html` | Конструктор персонажа и Конструктор Э.Г.О. |
| `office.html` | Офис |
| `admin.html` | Админ-панель: доступы, канон, пользователи, модерация, скрытое, журнал (см. «Администрирование») |
| `shirm-app/` | Ширма (React), собирается Vite в `dist/shirm.html` |
| `map-app/` | Редактор карт (React), собирается Vite в `dist/maps.html` — см. «Редактор карт» ниже |
| `docs/map-editor.md` | ТЗ редактора карт: решения, этапы и их статус, форматы файлов |
| `Assets/` | **весь контент сайта** — см. ниже |
| `site/` | общий код для всех страниц (см. ниже) |
| `scripts/` | генератор данных конструктора, копирование страниц в `dist/`, `canon-pull.mjs` (канон из Firestore → `Assets/`) |
| `firestore.rules` | **полные** правила Firestore — вставлять в консоль Firebase целиком |
| `vercel.json` | сборка, заголовки безопасности (CSP), перенаправления со старых адресов |

Старые адреса (`feats.html`, `grimoire.html`, `statuses.html`, `bestiary.html`, `equipment.html`,
`egogifts.html`, `lore.html`, `rules.html`, `custom.html`, `shirm-legacy.html`) больше не отдельные страницы —
`vercel.json` перенаправляет их в нужный раздел Базы знаний (`navigation.html#feats` и т. д.) или в Ширму.

### `Assets/` — контент по группам

```
Assets/
├── Rus/                     русский (основной) — Eng/ повторяет ту же структуру
│   ├── characters/          systems.json (реестр классов), classes.json, fixer.json, bloodarch.json, bloodfiend.json, feats.json
│   ├── items/               equipment.json, egogifts.json
│   ├── mechanics/           statuses.json, rules.json
│   ├── world/               lore.json, bestiary.json, world.json (карта Ширмы)
│   ├── articles/            статьи-фрагменты HTML (equipment-lore.html — «Лор и правила» снаряжения)
│   └── builder/             Builder_*.json — генерируются, руками не править
├── Eng/
├── Icons/                   иконки типов урона/статусов (Burn.png, Bleed.png, …)
└── Maps/                    канонический набор редактора карт (полы, стены, двери, объекты, scalable/ — вывески…)
```

- **Основной источник канона — Firestore** (коллекция `canon`, правится в `admin.html` → «Канон»).
  Файлы в `Assets/` — запасной вариант: сайт берёт их, если файл ещё не перенесён в Firestore или Firestore недоступен.
  Правка прямо в `Assets/` на сайте не появится, пока файл есть в Firestore — правьте в панели или уберите файл
  из Firestore («Убрать из Firestore»). Вернуть правки из панели в репозиторий: `node scripts/canon-pull.mjs`.
- Новый файл данных: положите его в подходящую папку и допишите строку в `DATA_GROUPS` в `site/i18n.js`
  (или запрашивайте сразу с папкой: `I18N.fetchData('articles/my-article.html')`).
- Новая иконка — в `Assets/Icons/`, в тексте карточек на неё ссылаются как `[Assets/Icons/Имя.png W:24]`.
  Старые ссылки вида `Burn.png` продолжают работать (rewrite в `vercel.json`).

### Классы и архетипы

- **Реестр классов** — `Assets/Rus/characters/systems.json` (в Firestore — `canon/Rus__characters__systems.json`):
  `[{ id, Name, BaseTitle, Base, Archetypes }]`. `Base` — файл основы класса (одна запись: способности класса),
  `Archetypes` — файл со списком его архетипов; оба лежат в `characters/`. Канонический архетип привязан к классу **файлом**.
- Новый канонический класс: `admin.html` → «Канон» → **«Новый класс»** — создаёт файл основы, файл архетипов
  (если их ещё нет) и запись в реестре. Произвольный новый файл — **«Новый файл»** (раздел, имя, язык). Такие файлы
  живут только в Firestore, пока их не скачают в репозиторий `node scripts/canon-pull.mjs`. Английский реестр не обязателен:
  без `Assets/Eng/characters/systems.json` берётся русский.
- **Пользовательский класс** — запись `custom_content` с `type: 'baseclass'` (раздел «Классы» в Базе знаний).
  Пользовательский архетип (`type: 'class'`) ссылается на класс полем `Class`: `id` из реестра (`fixer`) или
  `c:<id записи>` для пользовательского класса. Ссылка хранится в архетипе, а не в классе. Архетип без `Class`
  (старые записи) или со ссылкой на недоступный класс показывается у всех классов.
- В разделе «Архетипы» переключатель классов собирается из реестра (+ пользовательские классы в режимах «Кастом» и «Всё»).
  Конструктор персонажа (`builder.html`) показывает все классы реестра. У Фиксера и Кровососа полная авто-математика
  (метаданные из генератора), у остальных — общая: черта предыстории, увеличения характеристик на 4/8/12/16/19,
  слоты Э.Г.О., кость хитов из текста способности «Хиты» («Кость хитов: 1d8»). Пользовательские классы (`baseclass`)
  тоже доступны (с пометкой ⚠), а пользовательские архетипы привязаны к своему классу полем `Class`.
- После добавления типа `baseclass` опубликуйте свежие `firestore.rules`.

### `site/` — общий слой

- `firebase-config.js` — единственное место с конфигурацией Firebase (его же импортирует Ширма).
- `firebase.js` — инициализация Firebase для статических страниц (`app`, `auth`, `db`).
- `auth.js` — единая авторизация: вход, регистрация, выход, никнейм, проверка админа,
  **ограничение попыток: не больше 5 неудачных за 60 секунд** (`MAX_ATTEMPTS`, `WINDOW_MS`).
- `access-config.js` — email Кодера и разделы канона (общие для сайта и Ширмы).
- `canon-core.js` — формат хранения канона в Firestore (нарезка на куски), общий для админ-панели и Ширмы.
- `fields.js` — поля конструктора записей: словари (`DICT`), схемы по категориям (`SCHEMAS`), разметка и сбор формы,
  реестр классов (`CLASS_REGISTRY`, `canonSchemaFor` — схема файла класса по реестру).
  Общий для Базы знаний и админ-панели — новое поле или категорию добавляйте здесь.
- `ui.js` — окно «Настройки» (кнопка ⚙ в левом нижнем углу каждой страницы): язык и аккаунт.
  Открыть из кода страницы: `window.SiteUI.open('login' | 'register' | 'account')`.
- `i18n.js` — язык (RU по умолчанию), загрузка данных и перевод интерфейса.
- `i18n-en.js` — английский словарь интерфейса.
- `vendor/` — закреплённые версии marked и DOMPurify (раньше грузились с CDN без версии).

### Новая страница

```html
<script src="site/i18n.js"></script>            <!-- в <head>, первым -->
<script type="module" src="site/ui.js"></script> <!-- окно настроек -->
```
Данные — только через `I18N.fetchData('feats.json')`: путь подбирается сам
(`Assets/<Eng|Rus>/characters/feats.json` → `Assets/Rus/characters/feats.json`).
Вход — через `onAuth` из `site/auth.js`; своё окно входа на странице не нужно.

### Английский язык

- Данные: файл в `Assets/Eng/<группа>/` с тем же именем, что в `Assets/Rus/<группа>/`. Чего нет — показывается русская версия.
  Английская карта для Ширмы — `Assets/Eng/world/world.json`.
- Интерфейс: добавьте пару `'русская строка': 'English'` в `site/i18n-en.js`.
  Строки с числами/именами — через `patterns` в том же файле.

## Конструктор персонажа (`builder.html`)

- Логика — `site/builder.js`, общее ядро Э.Г.О. — `site/ego-core.js` (им же пользуется `egobuilder.html`;
  библиотека Э.Г.О. общая, хранится в браузере и доступна в слотах Э.Г.О. персонажа).
- Метаданные правил: `Assets/<Rus|Eng>/builder/Builder_feats.json`, `Builder_races.json`, `Builder_classes.json` —
  какие черты/расы/архетипы дают прибавки к характеристикам, выборы, другие черты, слоты, скорость, хиты,
  ссылки между чертами и снаряжение принадлежностей. **Не правьте их руками** — правьте
  `scripts/gen-builder-data.mjs` и запускайте `node scripts/gen-builder-data.mjs`.
  Черты, снаряжение и роды генератор находит **по имени** (`name: L(рус, англ)`) или по полю `id` записи, а не по порядку:
  записи канона можно добавлять и переставлять. Переименовали черту — поправьте её `name` в генераторе (он сам скажет, какую).
  Новая черта без метаданных просто не получает авто-расчёт. Конструктор тоже ищет снаряжение, роды и сохранённые
  выборы по имени, так что старые персонажи переживают перестановку записей.
- «Повысить уровень» — что изменится на следующем уровне (хиты, бонус мастерства, Свет, новые выборы и способности),
  после подтверждения открываются нерешённые выборы; история повышений — в досье (`levels` в состоянии).
- Слоты по правилам и «вне слотов»: всё, что выходит за лимиты, не проходит требования, а также пользовательские
  объекты (Firestore `custom_content` и загруженные JSON) попадает во второй ряд с пометкой «на усмотрение ДМ-а».
- Пресет v2 совместим с Офисом (поля `characterName`, `race`, `className`, `feats`, `desc`), полное состояние — в `builder`.
- Текущий персонаж всегда лежит готовым пресетом в `localStorage['builder.v2.preset']` — его подтягивает Офис.

## Офис (`office.html`)

- Логика — `site/office.js`. Данные: `offices/<id>` + досье агентов в подколлекции `offices/<id>/agents`.
- Участники добавляются **по никнейму** (реестр ников `nicknames/` + `users/` ведёт `site/auth.js`; ник уникален
  без учёта регистра). Старые офисы с доступом по email продолжают работать: участник сам переходит на ник,
  когда открывает Офис, а менеджер при открытии переносит старый массив `characters` в `agents`.
- Изменения приходят в реальном времени (`onSnapshot`); списки в документе меняются транзакцией целиком.
- Досье можно привязать к игроку — он сам обновляет его из конструктора или файлом.
- **Приватность досье проверяет сервер.** Полное досье (`offices/<id>/agents/<aid>`) читают только менеджер, владелец
  досье и Гл-Админ. Остальные участники читают карточку `offices/<id>/cards/<aid>` — в ней только поля, разрешённые
  настройками приватности офиса (`charSettings`); правила сверяют каждое поле карточки с досье и с настройками.
  Досье и карточка пишутся одной пачкой; при смене настроек менеджер переписывает все карточки. Старые офисы
  переводятся на карточки, когда их открывает менеджер (флаг `privacy: 2`); до этого участники видят только свои досье.
- **Награда контракта** (`reward`, Аны): когда контракт отмечен «Выполнен», награда одной транзакцией зачисляется в казну
  (запись журнала казны, `paidId`/`paidAmount` в контракте). Сняли отметку или изменили награду — выплата пересчитывается;
  отмена записи в казне снимает отметку об оплате. Над доской — статистика офиса (выполнено, провалено, заработано).
- **Журнал сессий** — вкладка «Журнал»: `offices/<id>/sessions/<sid>` (номер, название, дата, участники, итоги в Markdown).
  Пишет менеджер, читают участники.
- В «Казне» — график баланса по журналу операций.
- Казна в Анах; 1 Ан = 1 южнокорейская вона (KRW). Курс ₽/$ берётся с currency-api (jsDelivr) или open.er-api.com
  (разрешены в CSP в `vercel.json`), кэшируется на 6 часов; без сети — примерный курс.

## Редактор карт (`maps.html`)

Рисование карт для игры в Roll20, Foundry и других VTT, по духу — как Dungeondraft. ТЗ, порядок этапов и их статус —
**`docs/map-editor.md`**. Нужен вход в аккаунт, но всё хранится у пользователя: карты — в браузере (IndexedDB) и в файлах
`.pmmap`, свои наборы картинок — в браузере. В Firestore редактор ничего не пишет.

- Разработка: `npm run dev:maps` (вход не нужен), проверка типов: `npm run typecheck:maps`.
- Канонические ассеты — `Assets/Maps/`: **папки = категории и подтипы, файлы = разновидности**. PNG — 256 px на клетку
  (картинки меньше 256 px считаются одной клеткой), SVG — по размеру из `viewBox`. Настройки папки и файлов —
  необязательный `_meta.json` (название RU/EN, вид: `floor`, `wall`, `door`, `window`, `object`; `scalable`, `footprint`,
  `layer: "above"`…). Подробно — `docs/map-editor.md` §4.
- После изменения папок: `npm run gen:maps` — пересобирает `Assets/Maps/manifest.json` (сайт статический и не умеет читать
  папки; на Vercel это делает `npm run build`). Сейчас в `Assets/Maps/` — временные SVG-заглушки, их заменят рисунки команды.
- Экспорт: PNG / JPG / WebP (размер клетки 50–256 px, 70 — Roll20) и Universal VTT `.dd2vtt` (стены, двери, окна для
  динамического освещения).
- Рассчитан на ПК и планшет (мышь, сенсор, перо); на телефоне панели складываются в колонку, но рисовать там неудобно.

## Приложение и офлайн (PWA)

- `manifest.webmanifest` + иконки `Assets/App/` — сайт можно установить на телефон или компьютер
  («Добавить на главный экран» / значок установки в адресной строке). Ярлыки: База знаний, Конструктор, Офис, Ширма, Редактор карт.
- `sw.js` — service worker (регистрирует `site/i18n.js`, только по https; на localhost — с `?sw=1`).
  Свои файлы — «сначала сеть»: онлайн всегда свежая версия, без сети — последняя сохранённая; неизвестная страница
  без сети открывает главную. Firebase SDK с gstatic хранится в кэше (версия зашита в адрес). Стили, шрифты и иконки
  с CDN service worker **не трогает**: его запросы подчиняются `connect-src` из CSP (`vercel.json`), и перехват
  неразрешённого хоста ломает загрузку (так однажды пропали иконки Font Awesome). Добавляете хост в `CDN_OK` —
  сначала добавьте его в `connect-src`.
  Firestore и вход не кэшируются — без сети работают только уже открытые разделы с данными из `Assets/`.
- Новая страница: добавьте в `<head>` строки `manifest`/`theme-color`/`apple-touch-icon`, как у остальных;
  чтобы она открывалась без сети с первого раза — допишите её в `PRECACHE` в `sw.js`.
  Поменяли логику кэширования — увеличьте `VERSION` в `sw.js` (старые кэши удалятся).

## Мобильная вёрстка

Все страницы проверены на ширине 320, 360 и 412 px (горизонтальной прокрутки нет). Для новых блоков:
сетки — `minmax(min(Npx, 100%), 1fr)`, а не `minmax(Npx, 1fr)`; многоколоночные раскладки — в одну колонку
через `@media (max-width: 900px)`.

## Тесты

- `npm test` — модульные тесты (`tests/unit`: формат канона, сравнение текстов, ядро редактора карт).
- `npm run typecheck:maps` — проверка типов редактора карт.
- `npm run test:rules` — тесты `firestore.rules` на эмуляторе Firestore (`tests/rules`; нужна Java 11+, эмулятор
  поднимается сам). Меняете правила — добавьте тест.
- GitHub Actions (`.github/workflows/ci.yml`) запускает тесты, проверку типов редактора карт, сборку и тесты правил на каждый PR.

## Безопасность

- Любые данные из базы выводятся только экранированными (`esc`) или через DOMPurify.
- Права проверяет сервер (`firestore.rules`), а не интерфейс. После изменения правил их нужно
  опубликовать в Firebase Console → Firestore Database → Rules.
- Роли и права — см. «Администрирование». Старые документы `admins/<email>` больше не действуют.

## Администрирование (`admin.html`)

Ссылка на панель появляется в окне ⚙ Настроек у сотрудников. Английский интерфейс панели — раздел «Админ-панель» в `site/i18n-en.js`
(новые строки панели добавляйте туда же; пользовательские данные помечены `notranslate` и не переводятся). Логика — `site/admin.js`, канон — `site/canon.js`.

### Роли

| Роль | Где задаётся | Что может |
|---|---|---|
| **Кодер** | email в `CODER_EMAILS` (`site/auth.js`) **и** в `isCoder()` (`firestore.rules`) — менять вместе | всё; единственный, кто назначает и снимает Гл-Админов; его нельзя заблокировать |
| **Гл-Админ** | `roles/<uid>` `{ role: 'headadmin' }` | все права ниже + **скрытое**: приватные записи базы, все Офисы с досье, все Ширмы с «туманом войны» (просмотр и удаление); назначает Админов и выбирает их права |
| **Админ** | `roles/<uid>` `{ role: 'admin', perms }` | только выданные права |

Права Админа (`perms`): `canon` — список разделов канона (`characters`, `items`, `mechanics`, `world`, `articles`, `builder`);
`moderate` — видеть и править/удалять всю пользовательскую базу, включая приватное; `monitor` — статистика, список
пользователей, журнал; `ban` — блокировка пользователей. Человека для выдачи доступа ищут **по нику** (если он задал его
в ⚙ Настройках), **по email** (если заходил на сайт после обновления) или **по ID аккаунта** — его показывает admin.html
тому, у кого нет доступа, а все ID есть в Firebase Console → Authentication. Гл-Админ не может менять себя,
других Гл-Админов и Кодера; сотрудника с ролью может заблокировать только Кодер.

### Канон в Firestore

- `canon/<Rus|Eng>__<группа>__<файл>` — манифест (`version`, `chunks`, кто и когда правил);
  `canon/<…>/chunks/000…` — куски текста (документ Firestore ≤ 1 МБ, `world.json` больше).
- Первый запуск: «Канон» → **«Перенести всё из Assets»** (файлы, которые уже в Firestore, не трогаются).
- Редактор: файл → список записей → запись с переключателем **«Поля | Код»**. «Поля» — те же поля, что у конструктора
  в Базе знаний (схемы из `site/fields.js`), «Код» — JSON записи. Поля записи вне схемы при сохранении не теряются.
  Файлы без схемы (`world.json`, `Builder_*`, статьи) правятся только кодом. Ещё: загрузка/скачивание файла,
  «Из Assets» (откат к версии репозитория), «Копия русской» для перевода. Файлы классов из реестра получают поля
  основы или архетипов сами. «Новый файл» / «Новый класс» — см. «Классы и архетипы».
- Сохранение — одна пачка: куски + манифест + запись журнала. `version` растёт ровно на 1, поэтому одновременная
  правка двумя админами не затрётся — второй получит предупреждение.
- Сайт (`site/i18n.js`) читает канон через REST без входа, кэширует текст по версии (Cache Storage), так что
  повторный заход стоит одно чтение манифеста. Отключить для отладки: `?canon=off` (обратно — `?canon=on`).
- **Базовый мир (`world.json`) правится в Ширме.** У Админов с правом на раздел «Мир» (и у Гл-Админа, Кодера) ширмы
  группы «Базовый мир» открываются для правки обычным редактором Ширмы. Правки не сохраняются сами — кнопка
  **«Опубликовать в канон»** записывает в `world.json` только эту ширму (в новом формате `{ schemaVersion: 2, items }`,
  остальные ширмы файла не трогаются; загрузчик понимает оба формата). Если ширму успел изменить другой — предупреждение.
  «Туман войны» в базовом мире не секрет: `world.json` читают все. Код: `shirm-app/src/data/canon.ts`, `publishBaseScreen`
  в `shirm-app/src/data/screens.ts`; формат хранения общий с админ-панелью — `site/canon-core.js`.
- **Конструктор** сопоставляет черты, предметы и роды по имени: добавлять и переставлять записи безопасно.
  После переименования записи, на которую ссылается генератор, или новых метаданных: `node scripts/canon-pull.mjs` →
  `node scripts/gen-builder-data.mjs` → в панели «Загрузить файл» для `builder/Builder_*.json`.

### Мониторинг, блокировки, журнал

- `presence/<uid>` — ник, email, страница, последний и первый заход (сайт пишет не чаще раза в 10 минут).
  Аккаунты Firebase Auth целиком без серверного кода (тариф Spark) не перечислить — в списке те, кто задал ник или заходил.
- `bans/<uid>` — блокировка (навсегда или до `until`). Заблокированный читает сайт, но правила запрещают ему создавать
  и менять что-либо (база, Офисы, досье, Ширмы, ник, канон).
- `audit/` — журнал всех действий панели с прежними значениями. Менять записи нельзя, удалять может только Кодер.
  Кнопка ↶ в журнале откатывает выдачу/изменение/снятие доступа, блокировку и её снятие, видимость записи базы и
  удаление записи базы (модератор может восстановить запись от имени автора — это разрешают правила). Откат — тоже
  запись журнала (`audit.revert`); права на него те же, что на исходное действие.
- **Канон: сравнение.** «Сравнить» в панели несохранённых изменений показывает построчную разницу с версией в Firestore
  (или в Assets/, если файл ещё не перенесён); «Сравнить с Assets» — разницу рабочей копии с репозиторием.
  JSON сравнивается в одинаковом форматировании. Код — `site/diff.js` (алгоритм Майерса, тесты — `tests/unit/diff.test.mjs`).
- **Модерация:** записи, изменённые после прошлого визита, помечены «новое»; есть фильтр «Новые с прошлого визита»
  и кнопка «отметить всё как просмотренное» (время визита хранится в браузере).

### Локальная проверка с эмуляторами

`firebase emulators:start --only firestore,auth` (Firestore — порт 8085, Auth — 9099), затем открыть страницы
с `?emulator=1` на `localhost` (выключить — `?emulator=0`). На настоящем сайте этот режим не действует.
